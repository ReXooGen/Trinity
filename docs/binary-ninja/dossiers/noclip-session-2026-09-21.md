# No Clip PE 2944 — сесія 2026-09-21: реальне місце вимкнення колізії

Дата: 2026-09-21
Гра: Crimson Desert, PE 2944 (SHA-256 `6D348BE9…81FA7`)
Статус: колізія досі НЕ вимкнена. Але знайдено точне місце в коді, де рушій
резолвить фільтр і де виконується sweep — це те, чого не було в
[`noclip-session-2026-09-20.md`](noclip-session-2026-09-20.md).

Попередження про інцидент: під час сесії гра впала з `DEP Violation` на
`CrimsonDesert.exe+0x6A50FF0`. Причина — виклик внутрішньої функції рушія через
CE `executeCodeEx` поза контекстом game thread. Деталі в §6. Це правило більше
не порушувалось і не повинно.

## 1. Головний результат: послідовність резолву фільтра в integrator'і

Функція `VIBE_Locomotion_MoveUpdateIntegrator` (`0x144282080`) — та сама, яку
Trinity вже хукає як `hkMoveUpdate`. У ній `RBX` = moveOwner. Точна
послідовність (дизасемблер BN, view_1):

```asm
0x1442823db  mov  rcx, [rbx+0x48]        ; rcx = character-proxy компонент
0x1442823e2  call [rax+0x30]             ; -> RAX = сам proxy-об'єкт

0x1442823ec  lea  rdx, [QueryCollector::vftable]   ; rdx = vtable колектора
0x144282431  mov  [rbp+0x2a0], rdx       ; колектор №1 (на стеку)
0x14428248c  mov  [rbp+0x150], rdx       ; колектор №2 (на стеку)

0x1442824c5  mov  rcx, [rbx+0x48]        ; rcx = proxy компонент
0x1442824cd  mov  rdx, [rbx+0x38]        ; rdx = body id
0x1442824d0  call [rax+0x80]             ; -> RAX = об'єкт, чия vtable далі

0x1442826c9  call [rax+0x1f0]            ; сам collision sweep
```

Що з цього випливає:

- **`moveOwner+0x38` — це body id, а не покажчик.** У живому логу
  `800000000100001A`. Старші 32 біти — покоління/прапорці, молодші — id.
  Раніше в дос'є записано «body handle/ідентифікатор»; тепер це підтверджено
  формою і тим, що значення передається в `EDX`, а не в `RCX`.
- **`moveOwner+0x48` — компонент character-proxy з власною vtable.** Не сам
  менеджер. Саме тому `call [rax+0x80]` резолвить щось нове кожного разу.
- **Фільтр резолвиться щоразу заново**, а не зберігається. Ховати значення в
  полі body безглуздо — рушій його перезаписує (це вже було відомо з
  `body+0x54`, тепер ясно чому).
- **Колектори контактів створюються на стеку integrator'а.** Це локальні
  об'єкти, а не поля проксі. Отже підмінити їхню vtable можна точково, на час
  одного sweep, зсередини хука Trinity.

`LtCharacterProxyIntegrate` (VA `0x14530db68`) — це profiler scope цієї ж
функції, не окремий виклик.

## 2. Стек виклику sweep підтверджено живим дампом

`hkMoveUpdate` викликається з `RCX = [компонент+0x2C0]`. Компонент руху в
живій грі: `0x3EF701D0000`. Це підтверджує контракт PE 2944 і те, що Trinity
хукає правильну функцію.

Позиція проксі: `moveOwner+0x90` = `(x, up, z)` f32. Живий дамп:
`+0x90 = 441B50ED C41EC940 441B4DB9` → `(-635.145, 621.264, -474.904)`.

## 3. Vtable-слоти, зіставлені BN ↔ live

Живий `[moveOwner+0x48]` = `0x146A50FF0`, `[+0]` = `0x145BDA8D0` (= VA
`0x14324xxxx` + base — збігається з BN). Це доводить, що `.rdata` і `.text`
BN та живої гри збігаються побайтово.

| Слот | VA | Примітка |
|---:|---:|---|
| `+0x80` | `0x14324C200` | резолв об'єкта за body id (див. §5 — НЕ getBody) |
| `+0xF0` | `0x14324EE20` | `getBodyPropertyImpl`-подібний read |
| `+0xF8` | `0x14324F160` | — |
| `+0x100` | `0x14324F490` | — |

### Хибний висновок, який треба зняти

У дос'є 2026-09-20 записано «manager vtable `+0x80` → `getBody`». Жива
перевірка це **не підтвердила**: `call [rax+0x80]` з аргументами
`(manager, bodyId)` приймає `RCX=[moveOwner+0x48]` (компонент), а не менеджер.
Викликати слот `+0x80` напряму як `getBody(manager, handle)` не можна —
саме ця спроба призвела до крешу (§6).

## 4. `ResolveLocalPhysicsBody()` у Trinity зараз не може працювати

`src/game/teleport.cpp:1774-1811`:

```
ReadPtr(owner+0x48, &manager)      // насправді це proxy-компонент, не менеджер
ReadPtr(owner+0x38, &bodyHandle)   // насправді body id — маленьке число
ReadPtr(manager, &vtable)
ReadPtr(vtable+0x80, &getBody)
inGameImage(vtable) && inGameImage(getBody)   // <-- глухий кут
```

Два незалежні дефекти:

1. Об'єкт за `owner+0x48` живе в `.didata` (`0x146A50FF0`), а перевірка
   `inGameImage` приймає лише діапазон образу. Навіть правильний vtable був би
   відкинутий.
2. `owner+0x38` — це id, а не покажчик; `ReadPtr` по ньому безглуздий.

Функція повертає 0 завжди. Це не «поки не підключено» — це не може
запрацювати в поточній формі.

## 5. Що ще НЕ доведено

- Який саме слот повертає **сам об'єкт фільтра** (а не body). Кандидати —
  `+0xD8`/`+0xF0`/`+0xF8`/`+0x100`; потрібна перевірка, а не припущення.
- Де інстанціюється `hknpDisableCollisionFilter` і чи взагалі інстанціюється.
- Чи достатньо підміни vtable колектора на «нуль контактів», щоб проксі
  перестав коригуватися (це перевіряється лише живим тестом).
- Чи sweep викликається лише для локального гравця в цьому хуку.

## 6. Інцидент: DEP Violation 2026-09-21 00:03

```
Exception Code : 0xC0000005
Fault Address  : CrimsonDesert.exe+0x6A50FF0
RIP            : 0x0000000146A50FF0
Access Type    : DEP Violation (Data Execution Prevention violation)
RCX            : 0x800000000100001A   <-- body id, переданий як «аргумент»
Backtrace      : [00] CrimsonDesert.exe+0x6A50FF0
                 [01] 0x0000000006560028
```

`0x146A50FF0` — це `[moveOwner+0x48]`, тобто **дані**, а не код. CE
`executeCodeEx` виставив туди RIP, і DEP зупинив процес. Бектрейс з одного
кадру — підпис ін'єкції, а не шляху рушія.

Правило: внутрішні функції рушія не викликаються поза контекстом game thread.
Безпечні варіанти — читання пам'яті, або код всередині вже наявного хука
Trinity (`hkMoveUpdate` / `hkLocoStep`), який виконується на game thread.

Окремо: чотири попередні креші (23:09, 23:16, 23:23, 23:29) мають іншу
причину — `1B0_E658700.dll+0x3E060` (DLSS Frame Generation), до цієї роботи
вони не належать.

## 9. Повний ланцюг резолву body — тепер відтворюється чистим читанням

Раніше вважалося, що `getBody` вимагає виклику коду рушія. Це не так — це
**простий chunked-array lookup**, який відтворюється чистими читаннями пам'яті:

```
world singleton = data_146c8d0f8  (статична адреса)
world           = [data_146c8d0f8]                  (heap)
world_sub       = [world + 0x60] + 0x20             (клієнтський realm)
                  (або [world + 0x78] + 0x20 — серверний; вибір по TLS)
vtable          = [world_sub]                       = 0x145D12908
real getBody    = [vtable + 0x80]                   = 0x1439ED740
real getBodyProp= [vtable + 0xF0]                   = 0x144236570
real castShape  = [vtable + 0x1F0]                  = 0x1442B0BF0
```

`getBody(0x1439ED740)` — це:
```
slot = bodyId_lo32 & 0xFFFFFF          (для body id зі знаком, тобто біт 63=1)
chunkIdx = slot / 42
elem     = slot % 42
body     = [[world_sub+0x20] + chunkIdx*8] + elem*0xC0     (stride 0xC0 = 192)
```

Жива перевірка: body id `0x800000000100001A` → slot `26` → body `0x279E1BE8B80`.
Це означає, що **Trinity може резолвити body кожен тік без жодного виклику коду**
і без executeCodeEx.

Проксі-компонент `[moveOwner+0x48]` = `0x146A50FF0` — **статичний** (це
character-proxy manager), його vtable `0x145BDA8D0` — набір forwarding-thunk'ів,
кожен бере `PhysicsLock_Read_` і форвардить у реальний world vtable `0x145D12908`.

## 10. Де лежить collision filter info: `body + 0x90`

Живий body показує:
- `body + 0x30` = позиція (x, y, z)
- `body + 0xB0` = body id (8 байт) — підтверджено кодом integrator'а
- `body + 0x90` = **collisionFilterInfo** (uint32) = `0x0000401B`

Підтвердження: `hknpGroupCollisionFilter::isEnabled` (`0x144204080`, це слот
`[3]` vtable `0x145309EB0`) читає `[body+0x90]` для обох тіл пари і робить
перевірку груп.

Розклад filter info (uint32, group-фільтр):
- біти `[0..4]`   = collision group (5 біт)
- біти `[5..9]`   = sub-group
- біти `[10..14]` = group2 / subsystem group
- біти `[15..30]` = system groups
- біт  `[31]`     = не використовується group-фільтром

Гравець: `0x401B` = group `27`, sub-group `0`, group2 `16`, system `0`.

## 11. Логіка перевірки колізії (group filter `isEnabled`)

```
collide = ( table[groupA] & (1 << groupB) ) != 0
```
де `table` = `[filter_object + 0x24]`, 32 двоки (по одному рядку на групу).

Тобто **фільтр-інфо саме по собі не містить прапорця «вимкнено»**. Єдиний
per-body важіль — група (біти 0..4), а колізія визначається рядком таблиці
`table[groupA]`. Щоб вимкнути колізію гравця, треба поставити йому групу, чий
рядок таблиці дорівнює 0.

`hknpDisableCollisionFilter` (vtable `0x1453089D8`) — це окремий фільтр, чий
`isEnabled` (`0x1403600B0`) повертає 0 завжди. Але це **world-level** фільтр
(вимикає колізію для всіх), а не per-body. Для per-body noclip потрібен
group-фільтр + значення групи з нульовим рядком таблиці.

## 12. Що лишилося знайти

1. **Живий об'єкт group-фільтра** (щоб прочитати `[filter+0x24]` — таблицю
   32×32 і знайти групу з нульовим рядком). Скан writable-пам'яті на vtable
   `0x145309EB0` / `0x14530AF20` / `0x14530AF90` / `0x1453089D8` дав 0 хітів —
   фільтр або в `.data` (read-only), або глибоко у world (broadphase).
   Кандидатний шлях: знайти конструктор group-фільтра (той, що пише vtable) і
   прочитати default-таблицю, або пройти `[world+0xb70]` → vtable+0xc8 у
   castShape до об'єкта broadphase, де лежить фільтр.
2. **Чи перезаписує рушій `body+0x90`** щотіка. Якщо ні — одноразовий write
   тримається і його досить; якщо так — write треба тримати в хуку.
3. **Живий тест значення** (безпечний, з відновленням): зберегти `0x401B`,
   записати кандидата (наприклад групу з нульовим рядком або `0xFFFFFFFF`),
   перевірити падіння крізь підлогу, відновити `0x401B`.

## 14. Справжнє місце фільтра: `moveOwner + 0x40` (НЕ `body+0x90`)

Гіпотеза «фільтр у `body+0x90`» **спростована live-тестом**: запис значень у
`body+0x90` не вимкнув колізію. Дизасембл integrator'а показує чому:

```asm
0x144282697  mov  eax, [rbx+0x40]     ; rbx = moveOwner
0x14428269a  mov  [rbp+0x14], eax     ; input+0x14 = collision filter info
0x1442826c9  call [rax+0x1f0]         ; castShape(..., input, ...)
```

`castShape` отримує фільтр з `[moveOwner+0x40]` (це і є `m_collisionFilterInfo`
проксі). Живе значення: `0x0000401B` (група 27, sub 0, group2 16) — збігається
з `body+0x90` (дзеркало). `body+0x90` сам по собі на cast не впливає.

## 15. Група 22 (`0x16`) вимикає колізію — підтверджено live

Brute-force по 32 групах (запис групи g у `moveOwner+0x40` + `body+0x90`,
спостереження за Y):

| Група | Ефект |
|---|---:|
| 1 | просідання 0.5 |
| 21 | нестабільно (0–1.9) |
| **22** | **падіння з прискоренням — колізія вимкнена** |

Група 22 дала траєкторію `659.12 → 658.32 → 657.32` (прискорення), тобто
персонаж почав вільно падати крізь підлогу. Користувач підтвердив: «провалився
під землю».

## 16. Рушій ре-деривить фільтр щотіка — запис треба тримати

Після тесту рушій сам перезаписав `moveOwner+0x40` з `0x401B` на `0x401E`
(група 30 = стан «падає»). Тобто фільтр залежить від стану персонажа
(grounded=27, falling=30) і перераховується рушієм.

Висновок: noclip не може зробити «один запис». Він має **щотіка** в
`hkMoveUpdate` (до виклику оригінального integrator'а) записувати `0x16` у
`moveOwner+0x40`, і припинити — коли noclip вимкнено (рушій сам відновить
нормальну групу за станом).

## 17. Відкрите питання: стіни

Підтверджено лише вимкнення колізії з **підлогою** (падіння крізь землю). Чи
група 22 проходить крізь **стіни** — ще не перевірено. Потрібен тест біля стіни
в рамках прототипу. Якщо стіни тримають — шукати групу з нульовим рядком
таблиці (справжній «ні з чим не стикається»).

## 18. План реалізації (оновлений)

У `hkMoveUpdate` (game thread, вже наявний хук), коли noclip ON:

1. `moveOwner` = аргумент RCX хука (вже є).
2. Щотіка (до `oMoveUpdate`): `writeU32(moveOwner+0x40, 0x00000016)`.
3. Опційно синхронізувати `body+0x90` (не критично, бо cast читає +0x40).
4. noclip OFF: припинити запис — рушій сам відновить групу за станом.

Заувага про значення: `0x16` — це група 22 з очищеним group2/system. Оригінал
`0x401B` має group2=16. Чи критично очищати group2 — перевірити (можливо,
достатньо `0x4016`, щоб зберегти group2=16 і вимкнути лише групу).

Recovery (якщо гравець провалився): відновити `0x401B` в `moveOwner+0x40` +
`body+0x90`, підняти Y через teleport-write (`+0x90`/`+0x1A0`), обнулити
швидкість (`+0xC0`/`+0xD0`). Перевірено live — персонаж безпечно приземлився.
