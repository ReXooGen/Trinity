## 6. Findings

### 6.1 Blockers

**B1 — `kCharMgrAnchors` consensus is effectively gone (1 of 6 anchors match).**

`offsets.h:214-218` states the design intent: the anchors are "independently unique image-wide",
`Install()` cross-checks that they agree, "so a future update has to break all of them at once to
disable the feature, and a single stale survivor cannot quietly win the vote."

Measured against PE 2949 only `anchor[0]` matches (RVA `0x282F3A7`, resolving the manager global at
`0x146D696D8`); anchors 1-5 have **zero** matches. The 19:00 log confirms the consequence:
`player: char-manager successfully resolved (1 anchors verified).`

So the failure mode the design was written to prevent has already happened: a single surviving
anchor is now the only thing resolving the character manager, with no corroboration. If PE 2949's
`anchor[0]` site is coincidental rather than the intended call site, God Mode / Infinite Stamina /
Spirit / stat editing silently target the wrong global. This needs either re-derived anchors or an
explicit "single anchor accepted, corroboration unavailable" policy that is logged as a warning.

**B2 — `kSig_EquipEffectRefresh_Legacy` is ambiguous and resolved by first hit.**

The modern `kSig_EquipEffectRefresh` has 0 matches, so equipment code falls back to
`kSig_EquipEffectRefresh_Legacy`, which matches **twice** on PE 2949 (first at RVA `0x659510`).
`equipment.cpp` resolves it with `FindPattern` and does not call `CountMatches`, so the second
match is never reported. Hooking the wrong one of two candidates is exactly the
"one-match AOB … is not a callable function" hazard the plan's Review Focus calls out. This needs a
uniqueness assertion (fail closed when `CountMatches != 1`).

**B3 — the dye feature is unreachable and its engine contracts are missing.**

Two independent failures:

* Routes: `RenderDyeSlots`, `RenderDyeEdit` and `RenderDyeCustom` have **no call site anywhere** in
  `menu.cpp` (verified programmatically). Their route ids `dyeedit`/`dyecustom` have no dispatcher
  branch either, so if they were ever reached the dispatcher's final `else` would silently render
  the Player root instead. `dye_data.h` is included with the comment "legacy implementation
  retained out of startup/menu entry points" — the removal looks deliberate, but nothing in the
  routing is fail-closed about it.
* Contracts: all seven dye AOBs (`DyeApplySlot`, `DyeApplyBatch`, `DyeApplyBatch_Legacy`,
  `DyeUpsert`, `DyeUpsert_Legacy`, `DyeVisualSet`, `DyeVisualClear`, `DyeRecordRemove`) have **0
  matches** on PE 2949.

Net effect: 20 of the 208 inventoried controls (`RenderDyeSlots` 8, `RenderDyeEdit` 7,
`RenderDyeCustom` 5) are not reachable by a player, and even if they were, the dye engine they
drive cannot be located.

### 6.2 Risks (not yet proven broken)

**R1 — the durable inventory-container walk fails silently.** `kSig_InvCoreGlobal` has 0 matches.
`inventory.cpp:2377-2380` does `if (globAnchor) { ... }` with **no `else` and no log**, so the mod
quietly loses the "durable" container path that the registry comment describes as the reliable one.
The menu still works via the commit hook and lazy discovery, but this is an invisible capability
loss that a future audit would not see in the log at all.

**R2 — `kSig_EnvManager` and `kSig_EnvManager_Legacy` both fail (0 matches).** Weather is driven
through `WeatherRain`/`Snow`/`Dust`/`WindPack`, which do resolve, so this may be an unused fallback
— but it is unresolved and undocumented in the log.

**R3 — unknown route ids render the Player root.** The dispatcher's trailing `else RenderPlayer();`
(`menu.cpp:3309`) means any stale or typo'd route id shows the Player page instead of failing
visibly. `ui::PushMenu("loc_manage")` is handled, but the pattern is a latent mis-navigation hazard
(and is what would happen today for `dyeedit`/`dyecustom`).

**R4 — `kSig_JustCore` / `_Alt` are dead registry entries and the combat-timing detour is inert.**
`hkCombatTimingEval` (`player.cpp:799-805`) computes `orig`, reads `State` into an unused local, and
returns `orig` unchanged. Nothing in the menu exposes a parry feature anymore, so this is currently
harmless — but the hook is installed on every session for no effect, and the two `kSig_JustCore`
entries cannot ever gate a feature because no code references them.

**R5 — 12 crash reports on 2026-09-21 — RESOLVED as external (not mod-caused).** `Trinity_Crash.txt`
recorded 11 `0xC0000005` faults that day, including one at 19:13:51 from the build that was installed
at the time (`39FD38CE…`), plus a **12th at 19:58:13** from the first launch of the audited build
(`8B231897…`), triaged in §8.3. The owner has identified the cause: an **NVIDIA driver fault** — in
rare dark scenes the game falls to 2-3 FPS and then crashes.

This is consistent with the independent triage in §8.3, which found a write to a freed/corrupted
engine object inside **generic engine infrastructure with no mod hook or patch site anywhere near**
the faulting RVA, and consistent with the fact that **no two of the 12 crashes share a fault
address** (a driver/GPU instability pattern, not one deterministic code defect). The mod-side bisect
plan in §8.3 is therefore **not required**. Recorded as owner-attributed external cause; this audit
did not independently reproduce it, and the earlier reading of these crashes as a "material
regression signal" is withdrawn.

### 6.3 Observations

* `kSig_StatCommit` = 0 matches is **correct by design**: `player.cpp:821-830` only installs that
  hook when `UsesTu201CompatibleRevision()` is false, and PE 2949 takes the modern continuous
  stat-pin path. Not a blocker.
* `kSig_RegisterCrimeEvent` = 0 matches is likewise by design (`MayProbeLegacyCrimeEventDispatcherForRevision(2949) == false`), matching the log line "crime-event dispatch bypass unavailable on PE 2949".
* The remaining `NONE` entries are dominated by `_Pre201` / `_Legacy` variants selected away by the

### 8.3 Crash triage — launch #1, 2026-09-21 19:58:13

Caller (`find_call_references` on the live process):

Findings:

* The faulting code is a **two-instruction member constructor** (`mov [rcx], rax`) inside a
  **composite object constructor** that has **12 call sites** across the binary. It is generic
  engine infrastructure, not mod code.
* The pointer was **passed in** (`rcx`), and the enclosing constructor received it from *its* caller
  (frame `[03]` = `+0x3D0CD5`). So an engine caller handed a non-writable address to a constructor —
  the classic shape of a **freed or corrupted container element**, not of a bad hook.
* **None** of the mod's hook targets or patch sites is near RVA `0x47AF8C`; the nearest mod address is
  orders of magnitude away. A trampoline overlapping this function is therefore implausible.
* `CE`'s bulk AOB scan returned 0 hits even for `kSig_InvGetHolder`, whose bytes were independently
  read at `0x140212A100` in the same process — so **the scan API is unreliable on this title** and no
  conclusion may be drawn from its empty results.
